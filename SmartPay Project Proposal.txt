1. ABSTRACT / EXECUTIVE SUMMARY
================================================================================
The rapid proliferation of mobile financial services has transformed how individuals manage personal wealth, transfer funds, and pay for daily utilities. However, traditional mobile banking applications continue to suffer from critical security vulnerabilities—primarily over-reliance on static PINs or passwords that are susceptible to shoulder surfing, phishing, and SIM swapping. Furthermore, many mobile wallets lack seamless cloud synchronization across multiple user devices without creating excessive friction or compromising security barriers.

This project proposes "SmartPay," an advanced, secure, and cross-device mobile wallet application built using Flutter and powered by a Supabase PostgreSQL cloud infrastructure. SmartPay introduces a strict Dual-Factor Authentication architecture combining native hardware-backed local biometrics (Fingerprint verification) with secure application-level PIN validation. Beyond robust gatekeeping, SmartPay provides a full suite of next-generation financial tools: real-time peer-to-peer account transfers, a locked high-yield Safebox savings vault, instant micro-loan management, QR code scan-to-pay capabilities, a utility bill payment hub, and comprehensive security audit logging. By allowing users to securely access their accounts across any mobile device with cross-device session synchronization, SmartPay bridges the gap between high-security financial gatekeeping and seamless user experience.

================================================================================
2. BACKGROUND & STATEMENT OF THE PROBLEM
================================================================================
In contemporary fintech engineering, security and accessibility frequently exist at opposite ends of a spectrum. Existing mobile wallets face several limitations:
1. Vulnerability of Static Credentials: Single-factor PIN entry exposes users to visual interception in public spaces and credential stuffing attacks.
2. Device-Locked Silos: Many modern payment apps lock accounts strictly to a single physical device IMEI or installation instance. When a user changes phones or needs to access their funds from a secondary mobile device, they face complex re-registration barriers or total lockouts.
3. Fragmented Financial Management: Standard payment wallets focus solely on transfers and payments, requiring users to install separate applications for disciplined savings vaults or emergency micro-loans.
4. Lack of Biometric Auditability: Users rarely have visibility into failed or unauthorized login attempts occurring on their financial accounts across different devices.

3. AIMS AND OBJECTIVES
================================================================================
3.1 GENERAL AIM
The general aim of this project is to design, develop, and deploy a secure, responsive, and cross-device mobile financial application (SmartPay) that leverages hardware-backed biometric security and real-time cloud database synchronization.

3.2 SPECIFIC OBJECTIVES
1. Dual-Factor Security Gatekeeping: To implement a multi-layered authentication workflow combining hardware-level fingerprint scanning (via local_auth) and encrypted PIN verification.
2. Cross-Device Account Portability: To engineer a flexible account discovery and login system allowing users to securely log into their exact cloud profile from any mobile phone where SmartPay is installed.
3. Real-Time Financial Ledger: To build a high-speed transaction processing engine capable of executing peer-to-peer account transfers, bank deposits, and withdrawals with instantaneous balance updates.
4. Value-Added Wealth Tools: To construct a "Safebox" savings vault for locked funds preservation and a "Loan Management" engine for automated micro-credit disbursement and repayment tracking.
5. Utility & Retail Integration: To incorporate a comprehensive utility payment hub (Airtime, Data, Electricity, Cable TV, and Sports Betting) alongside a dynamic QR Code generator and camera scanner for retail checkout points.
6. Security Auditing: To implement a cloud-based audit trail (`biometric_login_logs`) that records every login attempt, method, success state, and device platform metadata for forensic auditing.

5. SCOPE AND LIMITATIONS
================================================================================
5.1 SCOPE OF THE PROJECT
• Development of a cross-platform Flutter application targeting Android and iOS.
• Integration with a cloud Supabase PostgreSQL instance for real-time profile, transaction, and audit logging.
• Implementation of local hardware biometric scanning (Fingerprint) and PIN authentication.
• Cross-device login capabilities ensuring seamless multi-phone accessibility.
• Financial simulation of transfers, savings vaults, micro-loans, and utility bill purchases.

5.2 LIMITATIONS
• Hardware Dependence: Fingerprint authentication requires the host device to possess functional biometric hardware (`local_auth` hardware availability). On unsupported devices, the application gracefully falls back to secure PIN verification.
• Clearing Network Sandbox: External inter-bank settlements and real-world utility vendor APIs are simulated using realistic transaction state management rather than live banking clearing nodes.

7. KEY FUNCTIONAL MODULES
================================================================================
1. Account Identification & Cross-Device Login Module:
   Allows users to enter their phone number on any device. The system normalizes digits across different international/local formats (`+234...`, `080...`) and queries cloud profiles to authenticate credentials and restore balance states immediately.

2. Dual-Factor Authentication Gatekeeper:
   Enforces PIN verification upon account identification and triggers local biometric fingerprint checks before authorizing high-value transfers or account settings changes.

3. Financial Assets Dashboard:
   Presents a consolidated view of Main Account Balance, Safebox Savings Balance, and Outstanding Loan Liabilities with toggle-able privacy masking (`isBalanceVisible`).

4. Peer-to-Peer Transfer & Payout Engine:
   Processes instantaneous account-to-account transfers and simulated bank payouts, generating auditable digital receipts with unique transaction reference IDs (`Ref: DEP/WTH/TRF-...`).

5. Safebox Vault & Micro-Loan System:
   Enables users to lock excess capital into a savings vault to enforce financial discipline, and provides an instant micro-credit disbursement engine that adds liquidity to the main wallet when needed.

6. Utility Bill Payment Hub:
   Dedicated checkout interface supporting Airtime renewals, Data bundle subscriptions, Electricity prepaid tokens, Cable TV payments, and Sports Betting account funding.

7. QR Scan-to-Pay Engine:
   Generates personalized account QR codes and provides a live camera viewfinder (`mobile_scanner`) to scan merchant or recipient QR codes for rapid checkout.

8. DATABASE SCHEMA & RELATIONAL MODELS
================================================================================
The cloud database structure consists of three core relational tables:

8.1 TABLE: profiles
• user_id (UUID, Primary Key): Unique account identifier linked to Supabase Auth.
• full_name (VARCHAR): Customer's registered full name.
• phone_number (VARCHAR, Unique): Primary contact and account identification key.
• pin (VARCHAR): Security PIN used for secondary authentication.
• account_no (VARCHAR, Unique): 10-digit unique wallet account number.
• balance (DECIMAL): Main spending wallet liquid balance.
• safebox_balance (DECIMAL): Total savings locked in the Safebox vault.
• loan_balance (DECIMAL): Total outstanding micro-loan debt.
• kyc_tier (VARCHAR): Customer verification tier (e.g., Tier 3 Verified).
• profile_picture_url (TEXT): Avatar image or DiceBear seed reference.

8.2 TABLE: transactions
• id (UUID, Primary Key): Unique transaction identifier.
• user_id (UUID, Foreign Key -> profiles.user_id): Owner of the transaction ledger entry.
• title (VARCHAR): Short transaction description (e.g., "Transfer to John Adam").
• subtitle (VARCHAR): Institution or reference details (e.g., "SmartPay • 9023456781").
• amount (VARCHAR): Formatted financial string with debit/credit indicators (e.g., "- ₦4,500.00").
• is_debit (BOOLEAN): Flag determining whether the transaction is an inflow or outflow.
• status (VARCHAR): Completion status ("Successful", "Pending", "Failed").
• created_at (TIMESTAMP): ISO-8601 timestamp of transaction execution.


8.3 TABLE: biometric_login_logs
• id (BIGINT, Primary Key): Auto-incrementing audit log entry ID.
• user_id (UUID, Foreign Key -> profiles.user_id): User attempting authentication.
• auth_method (VARCHAR): Type of check performed ("fingerprint" vs "pin").
• is_successful (BOOLEAN): Authentication outcome result.
• device_info (VARCHAR): Host device platform metadata (`defaultTargetPlatform`).
• created_at (TIMESTAMP): Timestamp of login attempt.
